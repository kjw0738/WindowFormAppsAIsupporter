# 회의록 자동 정리 모듈

## 구현 범위

회의 녹음본을 WinForms에서 선택하고, STT로 텍스트 변환한 뒤 사용자가 원문을 확인/수정하고 AI가 회의록 형식으로 자동 정리하는 기능을 구현한다.

## 사용자 흐름

1. `파일 선택`으로 회의 녹음 파일을 선택한다.
2. 회의 카테고리와 세부 주제를 선택하거나 세부 주제를 직접 입력한다.
3. 프로그램이 선택한 분야에 맞는 STT 힌트 용어를 자동으로 구성한다.
4. `STT 변환`을 눌러 녹음본을 텍스트로 변환한다.
5. `STT 원문 확인` 탭에서 변환된 내용을 확인하고 필요하면 수정한다.
6. `회의록 정리`를 눌러 의견 키워드 기반 회의록을 생성한다.
7. `저장`을 눌러 Markdown과 JSON 결과를 저장한다.

AI 회의록 정리가 실패했거나 API 키가 없어도 STT 원문이 있으면 저장할 수 있다. 이 경우 기록에는 `STT 원문만 저장됨` 상태로 표시되고, 나중에 기록을 불러와 API 정리를 다시 실행할 수 있다.

## 회의록 정리 방식

회의록 정리는 단순 장문 요약이 아니라, 회의 발화를 의사결정 단위로 분류한 뒤 병합하는 방식으로 처리한다.

처리 흐름:

1. STT 원문을 작은 구간으로 분할한다.
2. 각 구간에서 주제별 의견 키워드를 추출한다.
3. 추출 기준은 찬성, 반대, 추가, 삭제/제외, 수정, 새 주제, 결정, 담당 업무, 확인 필요이다.
4. 같은 주제의 의견을 병합한다.
5. 최종 회의록을 주제별 논의 정리 형식으로 생성한다.

최종 회의록에는 다음 항목이 포함된다.

- 회의 개요
- 주제별 논의 정리
- 찬성 의견
- 반대 의견
- 추가할 내용
- 삭제/제외할 내용
- 수정할 내용
- 새로 제시된 주제
- 최종 결정 사항
- 담당 업무
- 다음 회의 전 확인 필요

이 방식은 긴 원문을 그대로 요약하지 않기 때문에 토큰 초과 위험을 줄이고, 회의에서 실제로 중요한 의견 충돌과 결정 흐름을 더 명확하게 보여준다.

## AI 회의록 출력 품질 보정

STT 원문은 사용자가 직접 확인해야 하는 원자료이므로 의미를 추정해서 크게 수정하지 않는다. 대신 AI가 생성한 의견 추출 결과와 최종 회의록에는 저장 전 최소 보정을 적용한다.

- 회의록 프롬프트에서 한국어 문장은 한글로 작성하도록 명시
- `詳細`처럼 AI가 섞어 쓰는 중국어/일본어 한자 표현은 `상세`, `자세히` 같은 한글 표현으로 보정
- HTTP, DNS, API 같은 영어 약어와 기술 용어는 그대로 유지
- STT 인식 오류와 AI 출력 표현 오류를 분리해서 처리

따라서 `더詳細하게 하기` 같은 문구가 생성되는 경우는 STT 자체가 해당 문자를 만든 것이 아니라 AI 회의록 생성 단계에서 한자 표현이 섞인 것으로 판단한다. 파일은 UTF-8로 저장되며, `�` 같은 대체 문자가 없는 경우 인코딩 깨짐보다는 AI 출력 품질 문제로 보는 것이 맞다.

## 진행도 UI

긴 녹음 파일 처리, ffmpeg 다운로드/분할, 로컬 Whisper STT, AI 의견 추출은 시간이 걸릴 수 있으므로 진행 상태를 UI에 표시한다.

- 상태 라벨: 현재 처리 단계 표시
- 진행바: 처리 중에는 움직이는 진행바로 표시
- 구간 처리: `(현재/전체)` 메시지가 있는 경우 퍼센트 진행률로 표시
- 완료 시 `100%`로 표시
- 긴 작업 중 `취소` 버튼으로 현재 작업 중단 요청 가능

취소는 `CancellationToken`을 통해 STT, ffmpeg 처리, API 대기/재시도, 회의록 정리 흐름에 전달된다. 취소 시 이미 저장된 중간 캐시는 유지되므로 같은 원문을 다시 정리할 때 처리된 구간은 재사용할 수 있다.

## 저장 전 작업 보호

STT 변환이나 AI 회의록 정리 결과는 처리 시간이 길기 때문에 실수로 지워지면 사용자 손실이 크다. 이를 막기 위해 STT 원문 또는 AI 회의록이 변경된 뒤 저장되지 않은 상태를 추적한다.

- 새 녹음 파일 선택 전 확인
- 회의록 기록 불러오기 전 확인
- 폼 종료 전 확인
- 저장 완료 또는 저장된 기록 불러오기 시 미저장 상태 해제

사용자가 확인창에서 계속 진행을 선택한 경우에만 현재 작업 내용을 덮어쓴다.

## 긴 회의 녹음 처리

1시간 이상 회의처럼 녹음 시간이 길거나 파일 용량이 큰 경우, API 요청이 중간에 실패할 수 있다. 이를 방지하기 위해 다음 로직을 적용했다.

- 파일이 약 20MB를 넘거나 길이가 25분을 넘으면 긴 녹음으로 판단한다.
- `ffmpeg`를 사용해 10분 단위 MP3 조각으로 자동 분할한다.
- 각 조각을 순서대로 STT 처리한다.
- STT 결과는 `[구간 1]`, `[구간 2]` 형식으로 합쳐서 원문 확인 탭에 표시한다.
- AI 요약 API의 토큰 제한을 넘지 않도록 STT 원문을 작은 단위로 나눠 의견 키워드를 추출한다.
- 추출 결과를 최종 회의록으로 병합한다.

## ffmpeg 처리

긴 녹음 자동 분할과 로컬 Whisper용 WAV 변환에는 `ffmpeg.exe`, `ffprobe.exe`가 필요하다. 프로그램은 아래 순서로 도구를 찾는다.

1. `FFMPEG_PATH`, `FFPROBE_PATH` 환경 변수
2. 실행 파일 폴더
3. Windows `PATH`
4. 없으면 프로젝트 실행 폴더의 `AppData/Tools`에 portable ffmpeg 자동 다운로드

`ffmpeg`는 내부 전처리 도구로만 실행되며 별도 콘솔 창을 띄우지 않고 백그라운드에서 처리한다.

## API 키 설정

현재 구현은 회의록 정리 API는 Groq를 기준으로 하고, STT API는 공급자를 선택할 수 있다.

- 필수 환경 변수: `GROQ_API_KEY`
- 기존에 `XAI_API_KEY` 이름으로 Groq 키를 저장한 경우도 임시 호환한다.
- STT 공급자: `STT_PROVIDER=groq` 또는 `STT_PROVIDER=openai`
- Groq STT 기본 모델: `whisper-large-v3-turbo`
- OpenAI STT 기본 모델: `gpt-4o-mini-transcribe`
- 요약 기본 모델: `llama-3.3-70b-versatile`

선택적으로 아래 환경 변수로 모델명을 바꿀 수 있다.

- `STT_MODEL`
- `STT_CHUNK_MINUTES`
- `GROQ_CHAT_MODEL`
- `GROQ_CHAT_DELAY_SECONDS`
- `GROQ_MAX_AUTO_RETRY_SECONDS`
- `OPENAI_API_KEY`: OpenAI STT를 사용할 때 필요

선택한 STT 공급자의 API 키가 없으면 STT는 로컬 Whisper로 처리한다. 회의록 AI 정리는 `GROQ_API_KEY`가 있어야 사용할 수 있다.

## 설정 UI

프로그램의 `설정` 탭에서 현재 실행 환경이 어떤 값을 읽고 있는지 확인하고, 필요한 설정을 변경할 수 있다. API 키는 보안을 위해 프로그램 내부 파일에 저장하지 않고 사용자 환경 변수에 저장한다.

- API 키 등록 여부와 읽은 환경 변수 이름
- STT 모델명과 설정 출처
- AI 회의록 모델명과 설정 출처
- AI 요청 대기 시간과 설정 출처
- 로컬 Whisper 모델과 설정 출처
- ffmpeg 탐색/자동 다운로드 방식
- 환경 변수 등록 안내
- API 키, 모델, 대기 시간 입력 및 `설정 적용`
- 사용자 환경 변수 저장과 현재 실행 중인 앱 설정 즉시 갱신
- 환경 변수 `다시 읽기`

`설정 적용`을 누르면 현재 프로그램에는 즉시 반영된다. 이미 실행 중인 다른 프로그램에는 반영되지 않을 수 있으므로 필요하면 새로 실행해야 한다.

## API 요청 안정화

Groq Chat Completions 요청은 요청 전용 메시지 타입과 응답 전용 메시지 타입을 분리해서 처리한다.

- 요청 메시지: `role`, `content`만 전송
- 응답 메시지: `content`, `reasoning_content`, `reasoning`을 읽을 수 있도록 분리

이렇게 분리한 이유는 응답 전용 필드가 요청 JSON에 섞이면 API에서 `reasoning is unsupported` 같은 오류가 발생할 수 있기 때문이다.

## API 리미트 대응

긴 회의록 정리는 여러 번의 AI 호출이 필요하므로 분당 토큰 제한(TPM)에 걸릴 수 있다. 이를 줄이기 위해 다음 정책을 적용한다.

- STT 원문 해시 기준으로 구간별 의견 추출 결과를 `Data/summary-cache`에 저장
- 같은 원문을 다시 정리하면 이미 처리한 구간은 API를 다시 호출하지 않고 재사용
- 중간에 리미트나 오류가 발생해도 다음 실행에서 처리된 구간 이후부터 이어서 진행
- 구간별 의견 추출 요청 사이에 기본 20초 대기
- 최종 회의록 병합 요청 전에도 대기
- API가 `429 Too Many Requests`를 반환하면 응답의 `try again in Ns` 값을 읽어 자동 대기 후 재시도
- 최대 4회까지 자동 재시도
- AI가 잘못 정리한 결과가 캐시에 남아 같은 결과가 반복될 수 있으므로 `캐시 삭제` 버튼으로 현재 STT 원문에 연결된 요약 캐시를 삭제할 수 있다.
- 429 응답의 예상 대기 시간이 너무 길면 계속 기다리지 않고 자동 중단한다. 이미 처리된 구간은 캐시에 남기므로 나중에 다시 실행하면 이어서 처리할 수 있다.

기본 대기 시간은 아래 환경 변수로 조정할 수 있다.

- `GROQ_CHAT_DELAY_SECONDS`
- `GROQ_MAX_AUTO_RETRY_SECONDS`: 429 제한 발생 시 자동으로 기다릴 최대 시간, 기본값 120초

## 오류 안내 UX 개선

API 오류가 발생했을 때 원문 JSON 응답을 그대로 보여주면 사용자가 원인을 판단하기 어렵다. 그래서 WinForms UI에서 주요 오류를 한국어 안내로 변환한다.

- `429 Too Many Requests`: API 사용량 제한, 재시도 대기 시간, 캐시 재사용 안내
- `tokens per day`, `TPD`: 하루 토큰 한도 도달 안내, 출력 토큰 상한 조정 안내
- `401`, `403`, invalid API key: 환경 변수 키 등록 및 프로그램 재실행 안내
- `413 Payload Too Large`: 입력 크기 초과와 원문 정리 안내
- `400 Bad Request`, unsupported: 모델명 및 API 요청 형식 확인 안내
- AI 응답 본문 누락: 재실행 및 기본 모델 확인 안내

상세 오류는 함께 표시하되 길이를 제한해서 메시지 창이 과도하게 커지지 않도록 했다.

AI 회의록 정리 실패 시에는 단순 오류 안내에서 끝나지 않고 사용자 선택지를 제공한다.

- 다시 시도
- 캐시 삭제 후 다시 시도
- 설정 확인
- 닫기

`설정 확인`을 선택하면 프로그램의 `설정` 탭으로 이동해서 API 키, 모델, 요청 대기 시간 상태를 확인할 수 있다.

긴 회의록 정리에서 하루 토큰 한도에 자주 걸리는 경우, 이미 처리된 구간 캐시는 유지한 채 다음 설정으로 이후 요청량을 줄일 수 있다.

- `GROQ_PARTIAL_MAX_TOKENS`: 구간별 의견 추출 출력 상한, 기본값 500
- `GROQ_FINAL_MAX_TOKENS`: 최종 회의록 출력 상한, 기본값 1200
- `GROQ_SUMMARY_CHUNK_SIZE`: 회의록 정리 입력 구간 크기, 기본값 5500

이 값은 API의 `max_completion_tokens`에 반영되므로, 같은 원문을 정리하더라도 요청 토큰량과 출력량을 줄이는 데 도움이 된다. 단, 이미 하루 한도에 거의 도달한 상태에서는 한도 회복 전까지 같은 키/같은 모델로 계속 실패할 수 있다.

`GROQ_SUMMARY_CHUNK_SIZE`는 구간별 의견 추출 API 호출 수에 직접 영향을 준다. 샘플 원문 기준으로 3500자에서 5500자로 늘렸을 때 구간 수가 약 30~36% 감소했다. 너무 큰 값은 한 요청의 입력량을 키워 API 실패 가능성을 높일 수 있으므로 코드에서는 3000~8000 범위로 제한한다.

최종 회의록 병합 단계에서는 구간별 의견 추출 결과 중 `- 항목: 없음` 형태의 빈 의견 라인을 제외한 뒤 AI에 전달한다. 이 처리는 STT 원문, 화면 표시 내용, 구간별 캐시 원본을 수정하지 않고 최종 병합 요청 입력만 줄인다. 샘플 캐시 기준으로 최종 병합 입력량이 약 5~16% 감소했다.

AI 요청 간 대기는 실제로 직전 구간에서 새 API 요청을 보낸 경우에만 적용한다. 구간 의견이 캐시에서 재사용된 경우에는 불필요한 고정 대기를 건너뛰고, 직전 요청 이후 이미 설정된 대기 시간이 지났다면 바로 다음 단계로 진행한다. 따라서 재실행이나 캐시 복구 상황에서 체감 대기 시간이 줄어든다.

STT 변환 결과는 `Data/stt-cache`에 저장한다. 같은 녹음 파일을 다시 변환할 때 파일 경로, 파일 크기, 수정 시간, STT 공급자, STT 모델, 로컬 Whisper 모델, 음성 전처리 설정, STT 프롬프트 설정, 회의 카테고리/용어가 동일하면 이전 STT 원문을 즉시 재사용한다. 파일이나 설정이 바뀌면 다른 캐시 키를 사용하므로 새로 변환한다. 캐시 읽기/쓰기 실패는 기능 실패로 처리하지 않고 기존 STT 흐름을 계속 진행한다.

회의록 정리 중 생성된 구간별 의견 추출 결과는 두 단계로 캐시한다.

- 전체 원문 해시 캐시: 같은 STT 원문을 다시 정리할 때 즉시 재사용
- 구간 텍스트 해시 캐시: STT 원문 일부가 바뀌어도 동일한 구간 텍스트는 재사용

구간별 해시 캐시는 `Data/summary-cache/chunks` 아래에 저장된다. 이 구조는 원문을 조금 수정한 뒤 다시 정리할 때 API 호출 수와 토큰 사용량을 줄이는 목적이다.

회의록 정리 API에는 화면에 표시된 STT 원문을 그대로 던지지 않고, 정리 입력용 경량화 텍스트를 별도로 만든다. 화면의 원문은 수정하지 않는다.

- STT 환각성 대괄호 반복과 연속 반복 문구 제거
- 1글자 수준의 무의미한 줄 제거
- `[구간 n]` 구분과 실제 발화 내용은 유지
- 단어를 추정해서 고치거나 문장 의미를 바꾸는 보정은 수행하지 않음

이 처리는 긴 원문에서 불필요한 API 입력 토큰을 줄이고, Groq TPD 한도 소모를 완화하기 위한 성능 최적화이다.

## STT 안정화 방식

STT는 API 오류가 발생할 수 있으므로 다음 fallback 구조를 사용한다.

1. `STT_PROVIDER` 설정에 따라 Groq 또는 OpenAI STT를 먼저 시도한다.
2. API STT가 실패하면 같은 파일 또는 해당 구간을 로컬 Whisper STT로 자동 전환한다.
3. 선택한 STT 공급자의 API 키가 없으면 처음부터 로컬 Whisper STT를 사용한다.

긴 녹음 파일은 STT 공급자와 관계없이 기존 분할 로직을 재사용한다.

- 약 20MB 초과 또는 25분 초과 파일은 기본 5분 단위로 분할
- 분할 단위는 `STT_CHUNK_MINUTES` 환경 변수로 조정
- STT 요청 전에 ffmpeg로 음성 전처리를 수행
- 전처리는 모노/16kHz 변환, 저역/고역 필터, 음량 평준화를 포함
- 강한 노이즈 제거 필터는 일부 녹음에서 반복 문장이나 환각성 STT 결과를 만들 수 있어 제외
- `STT_AUDIO_PREPROCESSING=false`로 전처리를 끌 수 있음
- 각 구간을 순서대로 STT API에 요청
- `STT_PROMPT_ENABLED=true`인 경우에만 사용자가 선택한 회의 카테고리, 세부 주제, 자동 구성된 주요 용어 힌트를 STT API prompt로 전달
- 기본값은 `STT_PROMPT_ENABLED=false`이며, 이 상태에서는 음질 전처리만 적용하고 프롬프트는 보내지 않음
- 구간별 API 실패 시 해당 구간만 로컬 Whisper로 fallback
- STT API 429 대기 시간이 `GROQ_MAX_AUTO_RETRY_SECONDS`보다 길면 기다리지 않고 해당 구간을 로컬 Whisper로 fallback
- 로컬 Whisper fallback까지 실패하면 다시 API로 돌아가지 않고 중단한다. 따라서 `API 실패 -> 로컬 실패 -> API 재시도` 형태의 무한 루프가 발생하지 않는다.
- 사용자가 취소한 경우는 API 실패로 보지 않고 즉시 취소 처리한다.
- STT 결과를 `[구간 n]` 형식으로 합쳐 후처리

STT 결과는 화면에 표시되기 전에 기본 후처리를 거친다.

- 연속 공백 정리
- 과도한 빈 줄 제거
- 마침표/물음표/느낌표 뒤 줄바꿈
- 한국어 종결 표현 뒤 줄바꿈
- `[구간 1]` 같은 긴 녹음 분할 표기 유지
- `[끝]`, `[몇일이 없음]`처럼 STT가 무음/잡음 구간에서 만든 대괄호 반복 문구 제거
- 대괄호만 있는 문구가 전체 원문에서 5회 이상 반복되면 환각 문구로 판단해 제거
- `[구간 n]`이 아닌 짧은 대괄호 자막 조각은 제거
- AI 원문 보정에서 사용하는 `[확인 필요: ...]` 표시는 제거하지 않음
- 같은 문장이 3회 이상 연속 반복되면 1회만 남김
- 네트워크 강의에서 반복적으로 깨지는 기술 용어 사전 보정

이 후처리는 원문 내용을 바꾸기보다 읽기 좋은 줄 구조를 만드는 목적이다. 사용자는 `STT 원문 확인` 탭에서 결과를 직접 수정한 뒤 AI 회의록 정리를 실행할 수 있다.

기술 용어 보정 예시는 다음과 같다.

- `htb` -> `HTTP`
- `SMGP`, `S&TB` -> `SMTP`
- `D.S.` -> `DNS`
- `클라이터` -> `클라이언트`
- `데이터메이트` -> `데이터베이스`
- `리플레이어 탭` -> `replay attack`
- `마셋티케이션` -> `authentication`
- `스프피아` -> `spoofing`
- `매니저 미드런트` -> `man-in-the-middle`

사용자가 선택한 회의 카테고리와 세부 주제는 STT API prompt와 `원문 보정` prompt에 모두 반영된다. 프로그램은 `Data/meeting-category-terms.json`의 회의 도메인별 공통 용어와 세부 주제 용어를 자동으로 합쳐 STT 요청에 전달한다. 현재 사전은 인사/HR, 재무/회계, 법무/컴플라이언스, 마케팅/브랜딩, 영업/고객관리, 제품/기획, 기술/IT, 교육/강의, 음악/프로듀싱, 디자인/콘텐츠, 의료/보건, 제조/물류, 공공/행정, 연구/R&D를 포함한다. 세부 주제는 목록에서 선택할 수 있고, 목록에 없는 주제는 직접 입력할 수 있다.

회의 카테고리 사전은 코드가 아니라 JSON으로 분리되어 있으므로, 새 분야가 필요하면 `Data/meeting-category-terms.json`에 `category`, `topics`, `commonTerms`, `topicTerms`를 추가하면 된다. JSON 파일이 없거나 형식 오류가 있으면 프로그램은 코드에 남겨둔 최소 `일반 회의` 항목으로 fallback한다.

추가로 `원문 보정` 버튼을 통해 AI 기반 문맥 보정을 실행할 수 있다. 이 기능은 STT 품질 이슈로 단어가 뭉개졌거나 문장 구조가 어색한 경우, 앞뒤 문맥을 보고 보수적으로 교정한다.

장점:

- 뭉개진 STT 단어를 문맥상 자연스러운 표현으로 보정할 수 있다.
- AI 회의록 정리 전에 원문 품질을 높여 주제 분리와 키워드 추출 품질을 개선할 수 있다.
- 사용자가 직접 원문을 모두 고치지 않아도 1차 정리된 텍스트를 확인할 수 있다.

제한:

- 원문에 없는 발언, 결정 사항, 사람 이름을 추가하지 않도록 프롬프트로 제한한다.
- 문맥상 확실하지 않은 부분은 확정하지 않고 `[확인 필요: 원문]` 형태로 남긴다.
- 보정 후 기존 AI 회의록은 이전 원문 기준이므로 삭제하고 다시 생성하도록 처리한다.
- API 호출을 사용하므로 `GROQ_API_KEY`가 필요하고 긴 원문은 여러 구간으로 나눠 처리한다.

로컬 Whisper는 `Whisper.net`과 CPU 런타임을 사용한다. 처음 실행 시 모델 파일을 자동 다운로드한다.

기본 모델은 `base`이며, 아래 환경 변수로 바꿀 수 있다.

- `LOCAL_WHISPER_MODEL=tiny`
- `LOCAL_WHISPER_MODEL=base`
- `LOCAL_WHISPER_MODEL=small`
- `LOCAL_WHISPER_MODEL=medium`
- `LOCAL_WHISPER_MODEL=large-v3`
- `LOCAL_WHISPER_MODEL=large-v3-turbo`

## 프로젝트 내부 저장 위치

회의 카테고리와 STT 힌트 용어의 기준 데이터는 `Data/meeting-category-terms.json`이다. 앱 시작 시 이 JSON을 읽어 카테고리/세부 주제/용어 목록을 구성한다. JSON을 읽을 수 없는 경우에는 `Form1.cs`의 최소 fallback인 `일반 회의`만 사용한다. 따라서 새 회의 분야를 추가할 때는 코드보다 JSON을 우선 수정한다.

실행 파일 기준으로 자동 생성되는 데이터 폴더는 다음과 같다.

- `AppData/Tools`: ffmpeg 자동 다운로드 및 압축 해제 위치
- `AppData/Models`: 로컬 Whisper 모델 저장 위치
- `Data/meetings`: 회의록 Markdown/JSON 저장 위치
- `Data/summary-cache`: 회의록 정리 중간 결과 캐시 저장 위치

## 회의록 파일 관리

회의록 기록은 `Data/meetings` 폴더에서 관리한다. 저장 시 같은 ID를 가진 두 파일을 함께 생성한다.

- `.json`: 프로그램이 다시 불러오기 위한 기준 데이터
- `.md`: 사용자가 바로 열어 볼 수 있는 회의록 문서

AI 회의록이 아직 없는 경우에도 STT 원문만 저장할 수 있다. Markdown에는 AI 회의록 미생성 안내와 STT 원문이 함께 기록된다.

프로그램의 `회의록 기록` 탭에서 다음 기능을 제공한다.

- 저장된 회의록 목록 조회
- 키워드 검색: 녹음 파일명, AI 회의록, STT 원문에서 검색
- 날짜 필터: 생성 시작일/종료일 기준으로 기록 범위 제한
- 필터 초기화
- 선택한 회의록을 현재 STT 원문/AI 회의록 탭으로 불러오기
- 선택한 Markdown 회의록 파일 열기
- 선택한 기록 삭제
- 모든 기록 삭제
- 현재 STT 원문 기준 AI 요약 캐시 삭제
- 저장하지 않은 현재 작업이 있으면 불러오기/새 파일 선택/종료 전에 확인

삭제 시 같은 ID의 `.json`, `.md` 파일을 함께 삭제한다.

## Performance Cache Notes

- `Data/stt-cache`: 같은 녹음 파일과 같은 STT 설정에서는 전체 STT 원문을 재사용한다.
- `Data/stt-cache/chunks`: 긴 녹음 파일을 구간별로 처리할 때 성공한 구간 STT 결과를 저장한다.
- 구간별 STT 캐시는 중간 실패 후 재실행 시 이미 성공한 구간을 건너뛰기 위한 성능 최적화다.
- 캐시 키에는 파일 경로, 파일 크기, 수정 시간, STT 공급자, STT 모델, 로컬 Whisper 모델, STT 전처리/프롬프트 설정, 회의 카테고리/용어, 구간 번호, 전체 구간 수, 구간 길이 설정을 포함한다.
- `캐시 삭제 후 다시 시도`는 전처리 전/후 회의록 캐시와 구간별 의견 캐시를 함께 삭제한다.
- `AI_HTTP_TIMEOUT_SECONDS`: AI/STT 요청 타임아웃 설정이다. 기본값은 300초이며 코드에서 60~900초 범위로 제한한다.
- `AI_CACHE_RETENTION_DAYS`: 캐시 보관 일수다. 기본값은 30일이며 코드에서 1~365일 범위로 제한한다.
- `AI_CACHE_MAX_FILES`: 캐시 종류별 최대 파일 수다. 기본값은 1000개이며 코드에서 100~10000개 범위로 제한한다.
- 회의록 기록 검색은 `RefreshHistory` 시점에 검색용 문자열을 한 번 구성하고, 검색어 입력 중에는 미리 만든 문자열만 검사한다.
- 캐시 정리는 앱 실행 프로세스 안에서 한 번만 수행하고, 기록 검색 입력은 250ms 디바운스로 묶어 불필요한 반복 필터링을 줄인다.
- 기록 검색 인덱스는 미리 대문자로 정규화해 반복 검색 비교 비용을 줄이고, 목록 미리보기는 앞부분만 정리해 긴 STT 원문 전체에 정규식을 적용하지 않는다.
- 전체 기록 삭제는 각 JSON을 다시 읽지 않고 저장 폴더의 Markdown/JSON 파일을 직접 삭제한다.
- 오디오 변환은 STT 전처리 설정을 작업 시작 시 한 번만 읽고, 한 번 찾은 ffmpeg/ffprobe 실행 파일 경로를 재사용한다.
- 20MB를 초과한 녹음 파일은 길이 확인용 ffprobe를 생략하고 바로 분할 대상으로 판단한다.
- 회의록 목록은 `Utf8JsonReader`로 메타데이터와 요약만 경량 조회하고, STT 원문 검색이나 상세 불러오기 때만 전체 기록을 읽는다.
- 회의록 목록 메타데이터는 `.meta` 파일로 저장해 이후 새로고침에서 큰 JSON 본문을 다시 읽지 않도록 한다.
- STT 원문 검색 fallback은 필요한 기록만 늦게 읽고, 같은 목록 세션 안에서는 검색용 원문을 재사용한다.

네임스페이스가 팀 프로젝트와 다르면 `namespace`만 팀 프로젝트 기준으로 맞추면 된다.
